# 6つの柱 詳細チェックリスト

出典: Tom Long, *Good Code, Bad Code* (Manning, 2021)。各柱は書籍 Part 2〜3 の章に対応する。
全項目は読者(sei-lit)が日本語版(秀和システム, 2023)と照合済み(2026-08-11)。
今後項目を追加・変更する場合も同様に書籍と照合し、章・ページの対応は手元の検証メモに残すこと
(このリポジトリには転載しない)。

## 前提: 理論編の観点 (第2〜4章)

レビュー全体に横断的に適用する。

- **抽象化レイヤー** (第2章): 1つの関数・クラスは1つの抽象レベルの問題だけを扱っているか。
上位レイヤーに下位の実装詳細が漏れていないか。
- **コード契約** (第3章): 呼び出し側が守るべき前提条件が、ドキュメントの「小さな字」ではなく
型・シグネチャ・コンパイラで強制されているか。契約の「小さな字」に頼るほど誤用リスクが上がる。
- **エラー** (第4章):
  - 回復可能なエラー(ネットワーク断など)と回復不能なプログラミングエラー(バグ)を区別しているか。
  - エラーを握りつぶしていないか(fail fast / fail loudly)。
  - エラーが起き得ることが関数のシグネチャから分かるか(明示的な通知)。暗黙の例外だけに
  頼ると呼び出し側は気付けない。

## 柱1: 読みやすいコードにする (第5章)

- 名前は説明的か。読み手が中身を見ずに用途を推測できるか。
- コメントは「何をしているか」の重複ではなく「なぜそうしているか」を説明しているか。
- ネストが深すぎないか。早期リターンなどで浅くできるか。
- 1つの関数が複数の仕事をしていないか。行数より「一目で把握できるか」で判断する。
- 無名関数・強力な言語機能の使用が読みやすさを損ねていないか。 
- 命名・書式は周囲のコードと一貫しているか。

## 柱2: 驚きを避ける (第6章)

- マジックバリュー(-1 や空文字でエラーを表す等)を返していないか。
- null・未設定になり得る値が型(Optional 等)で明示されているか。
- 関数名から予想できない副作用を起こしていないか。
- enum の分岐は網羅的か。新しい値が追加されたときにコンパイラや網羅チェックで気付けるか。
- 呼び出し側が「まさかそうなるとは」と思う挙動(入力の破壊的変更など)がないか。 

## 柱3: 誤用しにくいコードにする (第7章)

- 可変にする理由がないものはイミュータブルになっているか(デフォルトは不変)。
- 汎用型の乱用(primitive obsession)をせず、意味のある専用型を使っているか。
- 同じ情報の「真実の源」が1つになっているか(単一情報源)。派生値を別々に持ち回っていないか。
- 一緒にしか意味をなさないデータがバラバラの引数で渡されていないか。データ構造で仕様を表現できているか。
- 呼び出す順序や組み合わせを間違えると壊れる API になっていないか。

## 柱4: モジュール化されたコードにする (第8章)

- 依存はハードコードせず注入(dependency injection)できるか。
- 具象クラスではなくインターフェース(抽象)に依存しているか。
- 継承が不適切に使われていないか。合成(composition)で置き換えられないか。
- 1つのクラスが多すぎる関心事を抱えていないか。
- 関連し合うロジックとデータが不自然に分散していないか。 

## 柱5: 再利用・汎用化しやすいコードにする (第9章)

- 特定の呼び出し文脈でしか成り立たない想定(assumption)が埋め込まれていないか。
- グローバル状態(可変な static 等)に依存していないか。再利用時に状態を共有してしまわないか。
- 関数の引数は必要なものだけを受け取っているか(オブジェクト全体 vs 必要なフィールド)。 
- 戻り値・例外の型が用途を不必要に狭めていないか。 
- 逆に、今必要のない汎用化で複雑になっていないか(過度な将来対応)。
- 関数、変数の公開範囲は適切か。それらが他の箇所から呼ばれたとしても、問題ないか

## 柱6: テストしやすいコードにし、適切にテストする (第10〜11章)

- テストは実装詳細ではなく公開 API(振る舞い)を検証しているか。
- 重要な振る舞い1つにつきテストケース1つになっているか。「関数ごとに1テスト」ではなく
「振る舞いごとに1テスト」。
- テストダブル(モック・スタブ・フェイク)の使い分けは適切か。本書はモック・スタブの乱用に
否定的で、可能なら本物またはフェイクの使用を勧めている。 
- テストが失敗したとき、何が壊れたかがメッセージから分かるか。
- テストは決定的か(実行順・時刻・乱数・外部環境に依存しないか)。
- エッジケース・エラー経路もテストされているか。
