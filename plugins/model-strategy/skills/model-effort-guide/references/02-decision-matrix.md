# 操作ルーティング × モデル/effort 決定マトリックス

本書は厳密なルーティング判定が必要な場合の解説であり、`skills/model-effort-guide/SKILL.md` の通常の軽量経路を上書きしない。マニフェスト・網羅的監査は明示的な高保証 opt-in 時だけ適用する。

基本原則: **高価なモデルは「判断」に、安価なモデルは「作業量」に使う。**
メインセッション(高性能モデル)のコンテキストを汚さないこと自体がコスト削減になる(キャッシュ効率 + 高単価トークンの節約)。

> **ルールの正本は `scripts/route-policy.mjs` の `RULES` / `routeOperation` / `auditManifest`。本書は解説であり、同期は `tests/route-policy.test.mjs` の 02 同期テストで検査される。**

## §1 ルール定義 (P0〜R4、先勝ち評価)

タスクを操作列に分解し、各操作に P0 → R0 → R1 → R2 → R3 → R4 の順で述語を当てはめ、最初に Y になったルールを採用する。判定は観測可能な述語の Y/N のみで行い、重要度・難易度の主観評価を挟まない。

| ルール | 定義 | 担当 (Claude Code) | 担当 (Codex) |
| --- | --- | --- | --- |
| **P0** | 対象外ゲート — 外向き・破壊的・履歴改変操作 (push / PR 作成 / rebase / reset / clean / リポジトリ外の状態変更)。担当決定の対象外とし、どの担当でも実行前にユーザー承認を要する | `approval-gate` | `approval-gate` |
| **R0** | 単発直接実行 — diff を生まない・許可リスト内の・単発 (同一サブタスク内で 1 回目) の読み取りコマンド。メインが直接実行する | `main-direct` | `main-direct` |
| **R1** | 取得・列挙・抽出 — 成果物が「所在・列挙・抽出結果」であり diff を生まず、意味解釈を要しない操作 (grep/glob、ファイル所在特定、依存列挙、既知パターン検索)。要約・評価・原因推定は含まない | `haiku-scout` | `scout` |
| **R2** | 既知検証手順の実行 — 事前に確定したコマンド (テスト・lint・ビルド) の実行と結果の事実報告。失敗の原因診断・デバッグ中の反復実行は R2 ではなく R4 | `haiku-scout` | `scout` |
| **R3** | 構造化契約付き変更 — diff を生む操作のうち、メインが**構造化仕様 4 フィールド (対象 / 期待する観測可能結果 / 変更可能範囲 / 検証方法)** を先に書き切ったもの。書き切れなければ R4 | `sonnet-implementer` | `implementer` |
| **R4** | デフォルト — 設計・技術選定・曖昧さの解消・失敗原因の仮説形成・デバッグ・レビュー統合・受け入れ判定・仕様が書き切れない実装。R4 に割り当てた際は「R0〜R3 のどの条件が N だったか」を記録する (`route-policy.mjs` の `reasons` に機械生成される) | `main` | `main` |

`kind` は `"search"|"enumerate"|"read"|"execute-verification"|"modify"|"judge"` のいずれか。先勝ち評価の正確な述語 (`producesDiff` / `outward` / `interpretationRequired` / `singleShot` / `allowlistedCommand` / `kind` / `spec`) は `scripts/route-policy.mjs` の `routeOperation` を参照。

## §2 git 操作の割り当て

| 操作 | ルール | 備考 |
| --- | --- | --- |
| `git status` / `git log -n <N>` / `git diff --stat` の実行と事実抽出 (単発) | R0 | §5 の許可リスト内。同一サブタスクで連鎖したら R1 |
| 同上の連鎖的・広域な実行 (2 手目以降、複数ブランチ横断など) | R1 | 「所在・列挙・抽出」の範囲を超えない限り |
| diff 本文の読解が受け入れ判定・レビュー入力になる場合 | R4 | 意味解釈を要するため R1 対象外。監査対象の原文・レビュー対象 diff はメインが自分で読む |
| commit 作成 | R4 (メイン直接) | Why (なぜこの変更か) を知るのはメインのみ。sonnet-implementer に実装〜commit を一括で出す場合は、コミットメッセージを仕様に前渡しする |
| push / PR 作成 | P0 | 対象外ゲート。担当に関わらずユーザー承認が必要 |

## §3 デバッグ・失敗診断の扱い

失敗の原因診断・デバッグ中の反復実行は R2 (既知検証手順の実行) ではなく **R4**。仮説形成・原因推定は判断そのものであり、「結論だけ回収する」委譲には向かない。**迷ったら分解しない** — デバッグをサブタスクに分割して一部だけ委譲すると、原因追跡に必要な文脈が失われる。

## §4 Web リサーチの分割

- 情報収集 (検索・ページ取得・要点抽出) は R1 相当。Sonnet サブエージェントの fan-out で並列化できる
- 情報源の信頼性評価・複数情報源の統合判断は R4。収集は量、統合は判断

## §5 R0 許可リストと連鎖昇格

R0 の許可リスト (有界形を必須とする): `git status` / `git log -n <N>` / `git diff --stat` / `ls` (非再帰) / 既知パス 1 ファイルの範囲 Read。

- 同一サブタスク内で **2 手目以降**に探索が続いたら R1 へ昇格する。「2 手目以降」は測定によって導出した閾値ではなく、「連鎖」という言葉が意味を持つための語義上の最小値 (1 回限りが単発の定義そのもの) であり、恣意的なパラメータではない。実際の委譲判断への効き方は `06-context-monitor.md` §「実測手段と限界」の実測節の観測対象とする
- 出力が想定を超える環境 (巨大な dirty tree など) では R0 を使わず R1 に落とす。有界形であることが R0 の前提であり、無界な出力が見込まれる時点で単発直接実行の対象外になる
- R1/R2 判定は「必ず新しいエージェントを 1 件起動する」という意味ではない。同じ目的の操作は 1 回の有界な依頼へまとめ、起動・親文脈複製・結果統合の固定費が直接実行を上回る小作業は R0 として扱う

## §6 R3 の構造化仕様 4 フィールド

diff を生む操作を R3 として委譲するには、メインが実装前に次の 4 フィールドを文章で書き切る:

1. **対象**: 変更するファイル・モジュール
2. **期待する観測可能結果**: 完了時に何が確認できればよいか
3. **変更可能範囲**: 触ってよい範囲・触ってはいけない範囲
4. **検証方法**: どう確認するか (テスト・lint・実行例)

1 つでも書き切れなければ R3 ではなく R4 (先にメインで仕様を固めるか、メインで実装する)。実装中に新しい設計判断が必要になったら、そこで停止して R4 へ差し戻す。

## §7 メインを Fable 5 にすべきか?

Fable 5 のコストは Opus 4.8 の約 2 倍（トークナイザは同一。`00-pricing.md` §1）。サブスクでも **usage credits = API 単価**（$10/$50。同梱期間は 2026-07-07 で終了。`00-pricing.md` §4）なので、純粋なコスト判断で使う:

- 次の場合のみ Fable 5:
  - 長時間の自律実行（夜間ラン・大規模マイグレーション）で、失敗・やり直しのコストがモデル差額を上回る
  - Opus 4.8 で 2 回失敗したタスク（やり直し 2 回 > 差額）
  - アーキテクチャ設計・最難関のデバッグなど「Fable 5 でしか差が出ない判断タスク」
- それ以外の日常開発は **Opus 4.8 (high) で十分**。定型実装・探索・レビューの検証 fan-out は Opus/Sonnet/Haiku に流す
- effort は `medium`〜`high` 起点（`01-effort-levels.md`: Fable 5 は low でも従来の xhigh 級）。`xhigh`/`max` 常用はクレジットの浪費
- セーフガードにより一部リクエストは **Opus 4.8 に自動フォールバック**される。Fable 前提のワークフローを組まない

## §8 委譲時の鉄則

- **仕様・制約・コンテキストは最初に全部渡す**。往復 1 回ごとにコンテキスト再送のコストがかかる (R3 の 4 フィールドはこの鉄則の具体化)
- 戻り値は「結論 + 根拠の要点」のみ要求する。生ログ・全文をメインに持ち帰らせない
- モデルを固定した `haiku-scout` / `sonnet-implementer` を使う。高価な親モデルを継承する Explore / general-purpose / fork 型をコスト削減目的で使わない
- 並列化は壁時計短縮が必要な独立タスクだけに限定する。利用上限を平準化したい通常時はキューし、同時稼働セッションを増やさない
- 高保証 opt-in 時は、委譲マニフェスト (予定担当 / 実効担当 / 状態 / 逸脱注記) にこの鉄則の実施結果を反映する。表示・監査の規定は [08-conductor-mode.md](08-conductor-mode.md) §0

## §9 Codex ランタイムでの読み替え

担当 (Codex) 列は `references/07-codex.md` §3 の `agents.<name>` の役割名 (`scout` / `implementer`) と、R4 を担うメインを指す。各役割のモデルと effort の対応は 07 だけに置く。hook による warn 強制は Claude Code のみ (`references/07-codex.md` に明記)。原則 (ルーティング表・マニフェスト・監査) は環境非依存で両対応。

## §10 R4 のサブタイプ (conductor mode, v0.3.0)

`MODEL_STRATEGY_MODE=conductor` のとき、R4 と判定された操作はさらに **R4-ctx / R4a / R4b** の 3 通りに機械分割される (正本は `route-policy.mjs` の `deriveR4Subtype`)。既定 (`judge-main`、未設定を含む) では発生せず、`routeOperation` の `subtype` は `null` になる。

| サブタイプ | 定義 | 担当 |
| --- | --- | --- |
| **R4-ctx** | `ctxClass` が閉じた許可リスト (会話文脈が本体の操作: commit 作成・ユーザー向け報告文) に所属する | メイン (conductor) 残留 |
| **R4a** | ctx でなく、判断パケット 6 フィールドが全て非空、かつ他行への `dependsOn` が空 (closed) | `judge` |
| **R4b** | ctx でなく、パケットが書き切れない、または `dependsOn` が非空 (adaptive) | セッション昇格の提案 |

詳細 (パケット規約・judge/judge-fable・失敗シグナル分類・受け入れの再ルーティング・R3 の contractRef/verificationRef 検査・scope-guard hook・4 つの限界の明記) は `08-conductor-mode.md` を参照。
