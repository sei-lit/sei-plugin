# dev-task-flow（機能開発・改善タスクの実行フロー）

このスキルは手順の順序と規模判定だけを持つ。各手順の中身はそれぞれの
所有スキル・設定に従い、ここに複製しない。

## 依頼の読み方

依頼は「目的 / 現状の問題 / 考えている解決案 / 制約」の形で来ることが多いが、全項目は必須でない。

- **目的** → goal-exploration 手順1の「目的の一文」にそのまま使う
- **制約** → 固定条件。明示された実装方法と同じ扱い（勝手に破らない。重大な問題があれば指摘のみ）
- **考えている解決案** → 候補であって決定ではない。目標探索の比較対象に含める
- 足りない項目は最も確からしい解釈を置き、報告でその旨を明示する

## 0. 規模を判定する

判定の軸はモジュール数ではなく「前例の有無」と「新しい公開契約の有無」。
レイヤー単位でモジュールを切るリポジトリでは定型的な機能追加でも常に複数モジュールに
跨るため、モジュール数で判定すると過剰に「大」へ倒れる。

| 規模 | 判定 | 実行する手順 |
| --- | --- | --- |
| 小 | 変更が1ファイル程度・新しい型なし・公開面の変更なし | 4（実装）と 5（検証）のみ。委譲・設計相談・model-effort-guide は使わない |
| 中 | 既存の類似実装を鏡写しにできる機能追加・変更（跨るモジュール数は問わない） | 全手順。設計相談は、迷う設計判断があるとき、または半日以上の見込みのときに方針確定前に1回 |
| 大 | 前例のない設計判断を含む / 新しい種類の公開契約（API スペックの追加・外部に公開するモジュールやフレームワークの追加・DI の新しい契約やデータアクセス層の新しい形） | 全手順。設計相談は必須（方針確定前と、手順5の検証後・最終報告前の2回） |

起動判定・規模判定を編集したら goal-exploration スキルの cases.md の回帰ケースで再検証する。

## 1. 目標探索

goal-exploration の規則に従う（起動判定・実装方法が明示された場合の扱い・
目的やスコープの変更を提案する際のテンプレートもすべてそちらが正）。
起動しないと判定した場合はこの手順を飛ばして手順2へ進む（「目的の一文」も作らない）。

## 2. 完了条件を決める

着手前に完了条件を観測可能な形で書き出す（ビルド・テスト・動作確認・PR 作成のどこまでやるか）。
依頼に書かれていれば転記、なければ自分で定めて最初の報告で提示する。既定値:

- PR 運用のあるプロジェクトでは PR 作成までを完了条件に含める
- UI の変更ではスクリーンショット等の表示確認を含めるかをここで決める
  （プロジェクトに撮影・QA の手順があればそれに従う）

## 3. 委譲と設計相談

- 中以上では /model-effort-guide をセッションに1回確認して委譲方針を決める
  （このフローからの参照は、同スキルの起動条件にある「明示的な利用依頼」として扱う）。
  委譲先の選定・アドバイザーへの渡し方・再相談の条件・待機中の振る舞いは
  model-effort-guide の §3〜5 に従う。ユーザーやセッションが別のアドバイザーを
  指定している場合はそちらを優先する（model-effort-guide §1 と同じ）
- 設計相談の2回目（大のみ必須）は手順5の検証後・最終報告前に行い、対象は設計判断の
  妥当性（構成・契約・見落とし）。差分の品質は手順6の self-review が担い、重複させない
- 設計アドバイザー: `which codex` が通れば `codex exec --sandbox read-only` を使う。
  モデルは指定せず、codex CLI の既定かプロジェクトの設定に従う。
  リポジトリ内のディレクトリから実行する（外だと trusted directory 判定で失敗する）。
  回答は `> file` で全文保存してから読む（tail で切ると前半が失われる）。
  codex が無ければ利用可能な代替（組み込みの advisor 等）を使い、報告で代替した旨を明記する
- 複数エージェントの監督・task DAG の調整が要るときだけ orchestration（Orca）を使う。
  単発の委譲は Agent ツールでよい（使い分けの基準は model-effort-guide にある）

## 4. 実装

- コメント・コミットメッセージの書き分けは CLAUDE.md の「実装知識の置き場所」に従う
- 設計の良否で迷ったときの判断基準は good-code-review の4つのゴール
  （毎回の全文適用はしない。品質ゲートは手順6の self-review が担う）
- コミットはプロジェクトに incremental-commit があればそれに従い、作業中に都度行う

## 5. 検証

- ビルドとテストを通す（コマンドはプロジェクトの CLAUDE.md が正）
- 失敗したら修正して再検証する
- 検証できなかったものを検証済みと扱わない。保証できた範囲とできなかった範囲を分けて報告する
- 中以上では、実装を終えた時点の検証（全体のビルド・テスト）をコミット後に `run_in_background` で起動し、
  完了を待たずに手順 6 のレビューを始める。レビューで直すと検証をやり直すことになるので、
  検証が通るのを待ってからレビューを始めない

## 6. self-review と PR

- レビューは検証と並行して回し、修正は 1 回にまとめる。レビューごとに修正と再検証を挟まない
  1. プロジェクトに PR 前レビュー用のコマンドやスキルがあれば、バックグラウンドで起動する
  2. その結果と検証の完了を待つ間に、self-review スキルと、プロジェクトにあれば review-checklist を同じ差分に当てる
  3. 検証の失敗・PR 前レビューの指摘・self-review の [must]・review-checklist の該当をすべて集めてから、まとめて直す
  4. 直した後の再検証は、修正が触れた範囲のテストと全体のビルドを 1 回。review-checklist が差分の変更で
     失効した場合（hook が拒否する場合）は、もう一度実行する
- まとめて直した差分が大きい（新しい型や分岐を足した）ときだけ、self-review を修正箇所に当て直す
- PR は「1 PR = 独立して説明・テスト・マージできる1つの変更」で分割する。
  分割の不利益（依存関係・rebase・CI 実行の増加）が上回るなら 1 PR でよい。
  複数に分けるなら pr-split、作成は pr-creator に従う
- 実装の PR から、E2E の変更と雛形を切り出し、雛形 → 実装 → E2E の順に積む
- PR を作るのは完了条件（手順2）に含まれる場合だけ。このフロー自体は PR 作成を強制しない

## 7. 最終報告

次の5点を簡潔に報告する。

1. 実施内容と主な設計判断（理由つき）
2. 検証結果（ビルド・テスト・self-review の結果と、保証できなかった範囲）
3. 作成した PR（作らなかった場合はその判断と理由）
4. アドバイザー指摘の採否と理由（相談した場合のみ）
5. 未解決事項
